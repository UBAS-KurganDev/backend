# UBAS Backend: правила работы с проектом

## Назначение и границы MVP

UBAS подбирает перелёты A → B → C с туристической остановкой B до трёх дней.
Основная аудитория — путешественники из РФ. Учитываются цена билетов, стоимость
въездной визы, туристическая ценность города, полезное дневное время и риск
самостоятельной пересадки. Поддерживаются единые и отдельные билеты.

- Авторизации, покупки билетов и бронирования в MVP нет.
- Отели и наземный транспорт не включаются в итоговую стоимость и рейтинг;
  цена отеля остаётся справочным полем.
- `date_from` / `date_to` ограничивают и вылет, и конечное прибытие включительно
  по местным датам соответствующих аэропортов.
- Между компонентами передаются коды городов IATA; не подменяйте их кодами аэропортов.
- Фабрика реального поставщика билетов подключается отдельно. Данные `routing/demo.py`
  вымышленные, не выдавайте их за реальные цены или визовые правила.

## Стек и стиль

- Python 3.14+, FastAPI, Pydantic 2, SQLAlchemy ORM/Core, Alembic.
- Зависимости управляйте через `uv`; обновляйте и `pyproject.toml`, и `uv.lock`.
- Соблюдайте строгий mypy и формат Ruff. Не отключайте проверки ради прохождения CI.
- Делите код по ответственности: короткие функции, понятные имена, явные зависимости.
- Доменные проверки возвращают результат или типизированную причину отказа.
  Учёт статистики и побочные эффекты выполняются отдельно.
- Не вводите универсальные фабрики, иерархии и отдельный класс на каждую проверку
  без конкретной потребности. Используйте существующие протоколы для заменяемых зависимостей.
- Не храните секреты в исходниках, документации, логах или тестовых фикстурах.

## Работа с БД: обязательные требования

- **Не добавляйте текстовый SQL**: никаких SQL-строк, `text()`,
  `exec_driver_sql()`, строковых запросов через драйвер или `.sql`-миграций.
  Стройте операции через SQLAlchemy ORM/Core и Alembic operations.
  Передавать построенные выражения в `execute()` допустимо.
- `asyncpg` используется как драйвер SQLAlchemy, а не как отдельный слой запросов.
- ORM-модели не должны проникать в API или доменный планировщик.
  Репозитории возвращают прикладные контракты.
- Сессия создаётся на короткую операцию. Не разделяйте одну `AsyncSession`
  между конкурентными задачами. Не держите транзакцию во время поиска билетов.
- Конкурентные гарантии обеспечиваются транзакциями, ограничениями БД и
  условными обновлениями, а не локальными Python-lock.
- Изменяйте схему новой Alembic-ревизией. Не переписывайте уже применённые ревизии.
  Ревизии должны включаться в wheel и работать вне исходного checkout.
- Сохраняйте существующие UUID, результаты и привязки ключей при миграциях.
  Для несовместимой смены схемы документируйте порядок остановки и обновления процессов.
- SQLite-каталог и PostgreSQL-очередь — отдельные хранилища с отдельными моделями.

## Инварианты очереди

- Один клиентский ключ всегда связан с тем же телом и запросом. Другое тело даёт 409.
- Все ключи сохраняются, даже когда одинаковые активные запросы используют одну задачу.
- Активные дубликаты запрещены уникальным индексом. Завершённый поиск можно повторить
  с новым ключом; повтор старого ключа возвращает прежнюю задачу.
- Захват задачи выполняется с `with_for_update(skip_locked=True)`.
- Запись результата и продление требуют актуального токена и неистёкшей аренды.
  Сроки аренды считаются по часам БД.
- Потеря аренды отменяет расчёт и дочерние поиски. Временная ошибка БД
  не должна навсегда завершать рабочий слот.
- Лимит попыток хранится в задаче. Ошибки входных данных не повторяются.
- Система имеет семантику at-least-once; не обещайте exactly-once для внешних вызовов.

## Инварианты планирования и API

- Сохраняйте контракт трёх ручек `/api/v1/queries`, `/{id}`, `/{id}/result`,
  если изменение контракта не является частью задачи.
- Проверяйте допустимый диапазон дат и валюту до постановки в очередь.
- API и worker используют один `PlannerConfig` через `UBAS_PLANNER_CONFIG_PATH`.
- Цена — Decimal; валюты не смешиваются. Для каждой разрешённой валюты
  задаётся эквивалентный масштаб `price_references`. По умолчанию доступна RUB.
- Интервалы времени считайте в UTC, местные даты и дневные окна — через IANA timezone.
- Проверяйте право выйти в город, срок оформления и актуальность визовых данных.
- Ограничивайте число городов, предложений, кандидатов, параллельных вызовов и время поиска.
- Провайдеры реализуют отменяемый async I/O; синхронная работа не блокирует event loop.
  Дочерние поиски должны отменяться вместе с родительским расчётом.
- Сохраняйте причины отсева, предупреждения и признак полноты поиска.

## Запуск и проверки

```shell
uv sync --locked
uv run --env-file .env ubas-migrate
uv run --env-file .env ubas-api
uv run --env-file .env ubas-worker
```

API и worker запускаются в разных терминалах. Приложение не читает `.env`
автоматически. Встроенный worker включается через `UBAS_EMBEDDED_WORKER=true`.

Перед завершением изменений исходников:

```shell
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
```

Для изменений поведения запускайте относящиеся к ним регрессионные проверки:

```shell
uv run --locked python -m unittest discover -s tests -v
```

PostgreSQL-проверки требуют `UBAS_TEST_DATABASE_URL` и отдельной БД с именем
`ubas_test_*`; они очищают очередь этой БД. Без переменной они пропускаются.
Не проверяйте конкурентные гарантии PostgreSQL только на SQLite или mock.
При изменении упаковки/миграций также выполняйте `uv build --no-sources`
и проверяйте миграции из пакета и переход с предыдущей схемы.

**CI содержит только Ruff (линтинг и форматирование) и mypy.** Не добавляйте
тестовый шаг в pipeline без соответствующего запроса пользователя.
В отчёте различайте выполненные проверки, пропуски и ограничения окружения.
