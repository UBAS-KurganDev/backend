# Поиск маршрутов по цене: ветви и границы

## Постановка

Ищем до 10 самых дешёвых допустимых предложений по известной стоимости
билетов и виз. В маршруте не больше четырёх рейсов (трёх промежуточных остановок).
Один билет может включать несколько рейсов и остаётся неделимым при составлении
маршрута. Дубли допустимы; ни длительность, ни город не дают преимущества при
равной/различной цене. Туристическая оценка влияет на предварительный выбор
городов поиска и фильтрует остановки от 12 часов, но не рейтинг готовых маршрутов.

Это best-first branch-and-bound с динамически вычисляемой нижней границей цены,
а не географическая Дейкстра. Расстояние между городами не оценивает стоимость
авиабилета достаточно надёжно для безопасных отсечений.

## 1. Покрытие топологии

SQLite-репозиторий сначала вычисляет прямые и обратные расстояния по числу рёбер.
В область поиска попадают города v с d(A,v)+d(v,C)<=4. Это необходимое условие
попадания в маршрут до четырёх перелётов внутри загруженной топологии; оно учитывает
направления и сохраняет циклы. Затем выбирается ограниченный набор городов.
Обоснование и источники графа — [topology.md](topology.md).
Описанный ниже обход остаётся fallback для источников только с destinations().

TopologyRepository.destinations возвращает исходящие города для набора городов.
Fallback строит четыре слоя направленных связей и применяет то же условие
d(A,v)+d(v,C)<=4. Четвёртый слой нужен для проверки достижения назначения.
Источник и конечный
город добавляются в область поиска; A → C запрашивается даже при пустой топологии.
В выбранной области запрашиваются все упорядоченные пары разных городов:
так поддерживаются не только отдельные рейсы, но и единые билеты на часть пути.
Внутренние города единого билета могут отсутствовать в топологии — для них
отдельно запрашиваются профили привлекательности.

Топология описывает согласованное покрытие, а не весь мировой рынок.
Её отсутствие не позволяет обещать поиск всех комбинаций отдельных билетов.
По согласованному решению владельца прототип ограничивает охват до max_hubs
промежуточных городов (по умолчанию 30). Профили загружаются для **всех** кандидатов
до отбора. Порядок: tourism_score по убыванию; затем количество прямых связей
A → v и v → C (0–2); затем сумма входящих/исходящих связей с остальными кандидатами
и конечными городами; затем код IATA по возрастанию для стабильности.
Неизвестная оценка равна 0. Туристический порог 60 при выборе городов не применяется:
низкая оценка по-прежнему допустима для короткой остановки.

A и C не расходуют квоту и включены всегда. Ограничение относится к концам
запрашиваемых билетов; внутренние остановки единого билета могут лежать вне списка.
Выборка не гарантирует глобально самые дешёвые маршруты. Результат содержит
search_scope и предупреждение search_scope_limited, если кандидаты были исключены.
complete=true означает завершение обработки **выбранной** области, включая все её
пары/даты. Ошибки провайдера и исчерпание вычислительных бюджетов остаются ошибками.

Отдельные защитные max_topology_cities=2000 и max_topology_edges=100000 ограничивают
подготовку топологии; их исчерпание — topology_discovery_limit и search_incomplete,
а не незаметное усечение кандидатов до загрузки оценок. Лимит городов применяется
к кандидатам path-репозитория или посещённым вершинам fallback; лимит рёбер — к
загруженным связям fallback и этапа разрешения равных оценок.

## 2. Получение предложений

Поиск ведётся по диапазону дат. Для межгородских календарных сдвигов запрашивается
расширение на два дня с обеих сторон; затем первые и последние местные даты
готового маршрута проверяются строго по пользовательскому окну.

Неполный ответ на диапазон разбивается на два непересекающихся диапазона.
Исходный ответ **заменяется** ответами дочерних диапазонов. Так сохраняются
реальные дубли провайдера, но не размножаются одинаковые наблюдения при повторе
запроса. Уточняются и пустые неполные ответы. Неполный ответ на один день
восстановить делением нельзя: внутридневная пагинация — ответственность адаптера.

Семафор ограничивает конкурентные вызовы одного экземпляра планировщика.
TaskGroup отменяет дочерние поиски вместе с родительским. Очередь задач обрабатывается
порциями, а не тысячами одновременно созданных coroutine. Есть общий бюджет
вызовов и предложений, лимит на направление, тайм-ауты вызова и всего поиска.
Урезание данных по бюджету не является доказанным отсечением.

## 3. Состояние поиска

Для каждого города билеты индексируются по моменту первого вылета в UTC.
Состояние содержит последовательность целых билетов, число уже использованных
рейсов, момент конечного прибытия и известную стоимость билетов.

Для продолжения из B бинарный поиск находит первый вылет строго после прибытия.
Максимальная длительность остановки не ограничена отдельно. Проверяется связность
по городу, поэтому смена аэропорта разрешена. Остановки >=12 часов требуют
оценки >=T; отсутствующая оценка равна 0. Проверяются как стыки между билетами,
так и рейсы внутри каждого билета.

Повторные города не запрещаются: глубина ограничена четырьмя рейсами.
Достижение конечного города создаёт кандидата, но не запрещает дальнейшее
продолжение, если ещё остаётся глубина. Разные последовательности покупаемых
билетов и реальные дубли не объединяются в одно состояние.

## 4. Нижняя граница

Пусть D[r][city] — минимальная известная стоимость билетов до конечного города,
если осталось не более r рейсов. При вычислении D игнорируются расписание,
туристические фильтры и все визовые расходы:

```text
D[0][destination] = 0
D[0][other] = infinity

D[r][city] = min(
    D[r-1][city],
    price(ticket) + D[r-segments(ticket)][ticket.destination]
)
```

Вторая часть берётся по билетам из city с количеством рейсов <=r.
Один единый билет расходует сразу несколько рейсов, но оплачивается один раз.
Неизвестная цена или отсутствующий курс дают вклад 0, как в итоговой сортировке.

Для частичного маршрута:

```text
lower_bound = known_ticket_cost_so_far + D[remaining_segments][current_city]
```

Почему это безопасно:

1. Удаление ограничений по времени и привлекательности может только уменьшить минимум.
2. Все известные компоненты цены неотрицательны; неизвестные считаются нулём.
3. Виза полностью исключена из границы, даже для уже посещённых городов.
   Поэтому будущий route-aware resolver может менять набор визовых расходов,
   не нарушая доказательство.
4. Валюта и округление билетов в границе те же, что при построении результата.

Недостижимый во времени дешёвый путь делает границу слишком оптимистичной,
но никогда не завышенной. Это увеличивает работу, а не теряет лучшие маршруты.

## 5. Раскрытие и остановка

Приоритетная очередь раскрывает состояние с минимальной нижней границей.
Готовый кандидат проверяется по местным датам, получает визовые компоненты,
итоговую известную сумму и попадает в текущую десятку.

Пока найдено меньше десяти реальных допустимых предложений, ценового порога нет.
После заполнения десятки порог — цена самого дорогого из этих десяти.
Ветвь можно отбросить только если её lower_bound строго больше этого порога.
Если минимальная граница всей очереди выше порога, поиск завершён доказанно.

Пример: ветвь с нижней границей 1000 дала реальную цену 9000.
Ветвь с границей 2000 не отсекается. Её реальная цена может оказаться 3000.
Сравниваются границы с **реальными результатами**, а не только друг с другом.

Равные цены не имеют обязательного порядка. Текущая реализация сохраняет строгую
проверку «>» и может исследовать равные границы дополнительно.

## 6. Полнота, сложность, ограничения

Память: индекс O(N), таблица границ O(4V), ограниченная очередь состояний.
Построение индекса O(N log N), таблицы границ O(4N).
В худшем случае число комбинаций до четырёх билетов экспоненциально:
границы цены и бинарный поиск уменьшают работу, но не отменяют худший случай.

Ценовые доказанные отсечения не делают поиск неполным.
Превышение лимита состояний/кандидатов/очереди/предложений, неустранённая неполнота
источника или тайм-аут приводят к IncompleteSearchError. Карточки такого поиска
не публикуются. Ответ «маршруты не найдены» возвращается только после полного
успешного поиска в согласованной области.

Регрессия сравнивает цену и количество всей выдачи с независимым полным
перебором на случайных малых графах. Отдельно проверены единые билеты, циклы,
дубли, недостижимая оптимистичная граница, неизвестные расходы и бюджеты.
Реальное покрытие источников и предельная задержка остаются OPEN-02/OPEN-03.
