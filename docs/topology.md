# Сборщик топологии

Сборщик — отдельная CLI-команда Python. Он запускается при подготовке или обновлении
каталога, а не внутри HTTP-запроса пользователя. API и worker продолжают читать SQLite
через существующие независимые репозитории. PostgreSQL-очередь не затрагивается.

## Источники и смысл данных

Направления загружаются из публичного [Fly Where To? API](https://flywhereto.com/mcp).
Его владелец собирает таблицы направлений аэропортов из Wikipedia; это не официальное
расписание. Используется read-only инструмент destinations_from, без фильтра типа
обслуживания и без запросов цен/покупки. Браузер и API-ключ не нужны.

Соответствия аэропорт → город, география и IANA-зоны берутся из открытых справочников
[аэропортов](https://api.travelpayouts.com/data/en/airports.json) и
[городов](https://api.travelpayouts.com/data/en/cities.json) Travelpayouts.
IATA города не выводится из названия или кода аэропорта. Например, текущий справочник
относит SVO, DME, VKO и ZIA к MOW; все помеченные flightable аэропорты выбранного города
запрашиваются, включая аэропорт с успешным пустым ответом.

Связь означает: источник упоминает возможное прямое направление между аэропортами.
Это не обещание рейса на конкретную дату. Сезонные, чартерные, будущие и приостановленные
связи сохраняются вместе с kinds в снимке. Их доступность подтверждает билетный
провайдер; из одних текстовых меток нельзя безопасно вывести календарь работы.

Снимок содержит ссылки на источники и атрибуцию Fly Where To? / Intuitive Bricks AB
и Wikipedia (CC BY-SA). При распространении полученной базы сохраняйте атрибуцию
и условия исходных данных. В репозиторий не коммитится мировой массив данных.
FlightsFrom и FlightConnections при проверке отклонили прямую загрузку; адаптер
не пытается обходить их ограничения. OpenFlights 2014 не используется как актуальная база.

## Быстрый запуск

Рабочий набор городов хранится в `config/topology-cities.json`. Он включает
города вылета из РФ, пересадочные узлы и дальние направления. Обновить весь набор:

```shell
uv run --locked python -m ubas_backend.topology --cities-file config/topology-cities.json --max-airports 200 --snapshot ./var/topology/expanded-new.json --catalog ./var/topology-catalog.sqlite3
```

Снимок должен иметь новое имя. После успешной загрузки обновите путь снимка
у скрапера и перезапустите worker. Состояние выполненного расширения и ограничения
поиска описаны в [отчёте об охвате](topology-coverage.md).

Минимальный пример для семи городов:

```shell
uv sync --locked
uv run --locked python -m ubas_backend.topology --cities MOW SVX ALA TAS DXB IST TYO --snapshot ./var/topology/initial.json --catalog ./var/topology-catalog.sqlite3
```

Выполненный 04.11.2026 запуск получил 13 исходных аэропортов, 1291 уникальную
направленную связь городов и географию 624 городов. Это наблюдение конкретного
запуска: количество со временем меняется.

Выберите каталог в .env:

```dotenv
UBAS_CATALOG_PATH=./var/topology-catalog.sqlite3
UBAS_AGENT_TOPOLOGY_SNAPSHOT_PATH=./var/topology/initial.json
```

В Compose файл уже находится внутри монтируемого ./var. Миграция PostgreSQL не
нужна для этого изменения; обычная подготовка очереди всё ещё требует ubas-migrate.
Для расширенного набора укажите вместо initial.json имя его созданного снимка.
Перезапустите API/worker при изменении пути. Билетный провайдер подключается отдельно;
сборщик сам не включает и не заменяет его.

--cities принимает **города**, не аэропорты. Набор задаёт города, чьи исходящие связи
собираются полностью относительно выбранного источника. Достигнутые города получают
географию, но их исходящие направления не обходятся автоматически. Для расширения
покрытия явно добавьте их в следующий запуск. Это позволяет контролировать размер
графа и нагрузку, не выдавая частично обойдённый мир за полную базу.
`--cities-file` принимает JSON-массив тех же кодов и взаимоисключается с `--cities`.
`config/topology-pending-cities.json` — отдельный отчёт об ошибках 05.11.2026,
а не список для автоматического импорта. Ошибки нужно устранить до добавления
этих городов в рабочий набор.

## Проверка снимка до записи

Можно сначала только скачать:

```shell
uv run --locked python -m ubas_backend.topology --cities MOW SVX --snapshot ./var/topology/review.json
```

А затем импортировать проверенный снимок без сети:

```shell
uv run --locked python -m ubas_backend.topology --from-snapshot ./var/topology/review.json --catalog ./var/topology-catalog.sqlite3
```

Имя JSON должно быть новым. Для каждого обновления используйте отдельное имя:
старый снимок не перезаписывается. Файл публикуется атомарно после завершённой
записи; файловая система должна поддерживать hard links (NTFS/ext4 и другие).
Снимок сохраняется **до** импорта. Его наличие подтверждает успешную загрузку,
а применение подтверждается успешным завершением команды. При ошибке импорта
можно повторить --from-snapshot. Сохраняйте архив: метаданные источника и время
живут в JSON, существующая схема SQLite не расширяется.

## Проверки и атомарность

Отдельные успешные сборы **непересекающихся** городов можно объединить без сети:

```shell
uv run --locked python -m ubas_backend.topology --merge-snapshots ./var/topology/mow.json ./var/topology/svx.json --snapshot ./var/topology/combined.json --catalog ./var/topology-catalog.sqlite3
```

При таком обновлении используются только явно перечисленные проверенные снимки.
Повторный город, противоречивая география или разная атрибуция вызывают ошибку
до записи БД. Время наблюдения каждого аэропорта сохраняется; объединение не
делает старые наблюдения свежими. Итоговый снимок публикуется перед одной
транзакцией импорта. Города с неудачным сбором не добавляются как пустые.

Проверяются IATA, IANA timezone, исходный аэропорт, количество направлений,
отсутствие фильтра/обрезки, типы обслуживания, уникальность аэропортов и полнота
запроса всех аэропортов выбранных городов. Неизвестное соответствие — ошибка всего
сбора; город или часовой пояс не подставляются автоматически.

Обновление SQLite — одна короткая SQLAlchemy-транзакция после сетевой работы:

1. Добавить отсутствующие географические профили с tourism_score=0 и пустыми визами.
2. Удалить старые исходящие связи **только** выбранных городов.
3. Вставить новые направленные связи, объединив аэропорты одного города и дубли.

Существующие профили сохраняются целиком: положительные оценки, визы и справочные
поля не стираются. Связи других исходных городов остаются. Обратные связи не
выдумываются. Ошибка записи откатывает и удаление связей, и добавление профилей.
Успешный пустой ответ очищает связи соответствующего города; ошибка источника —
никогда. Повторный импорт того же снимка идемпотентен.

Команда явно разрешает заменить связи выбранных городов снимком, в том числе
историческим. За выбор свежего снимка отвечает оператор; два параллельных импорта
сериализуются SQLite, последняя успешно записанная версия становится текущей.
Пустая новая БД при ошибке инициализации возможна, прежние данные не очищаются.
Не направляйте --catalog на другую прикладную БД.

## Лимиты и отказ источника

--max-airports по умолчанию 100, допустимо 1…1000. Он проверяется до вызовов направлений.
--interval по умолчанию 1 секунда между последовательными вызовами источника
(допустимо 0.25…60). Это один сборщик без параллельных браузеров.

Общий сетевой этап ограничен 600 секундами, отдельный вызов направлений — 30.
Один ответ справочника ограничен 12 MB, ответ направлений — 4 MB, весь снимок —
100000 аэропортовых связей. HTTP 403/429/5xx, таймаут, отмена и нераспознанный формат
завершают команду с ошибкой без импорта. Автоматического агрессивного повтора нет.
При 429 учитывайте Retry-After перед следующим запуском.

## Использование графа планировщиком

SqliteTopologyRepository дополнительно реализует PathTopologyRepository.
Для каждого запроса вычисляются кратчайшие числа рёбер:
d_start[v] из исходного города и d_finish[v] до конечного на обратном графе.

Город остаётся кандидатом, если:

```text
d_start[v] + d_finish[v] <= 4
```

Если маршрут A → … → v → … → C укладывается в четыре перелёта, суммы кратчайших
расстояний не могут превышать число его рёбер. Значит, условие не удаляет ни один
такой маршрут **в имеющейся топологии**. Направления важны; циклы разрешены.
Цена, туризм, время и географическое расстояние при этом не учитываются.
Сложность — O(V+E). Лимит городов применяется после этого отбора.

Для собранного примера SVX → TYO остаются ALA, DXB, IST, MOW и TAS вместо всех
достижимых городов мира. Для более широкого графа владелец согласовал выбор
до max_hubs городов по привлекательности, затем связности. Это ограниченный
охват search_scope, а не ошибка. Внешние реализации только с destinations()
используют четыре слоя связей и тот же отбор по достижимости назначения.

Единый билет A → C всегда запрашивается отдельно и может содержать города вне
топологии. Для комбинаций отдельных билетов полнота ограничена загруженным графом.
География города в БД не означает, что загружены его исходящие направления.
Расширение покрытия увеличивает число запросов билетному провайдеру и может
потребовать пересмотра бюджетов: сборщик сам их не повышает.

На расширенной базе проверенные направления дают 67–69 промежуточных городов,
из которых теперь выбираются до `max_hubs=30`. Полнота результата относится к
запросам между выбранными городами и конечными точками. Сбор билетов всё ещё
запрашивает все эти пары и уточняет даты. Лимиты запросов/времени сохраняются;
при их исчерпании ответ — `search_incomplete`. Время холодного поиска с 30 городами
не измерено: выбранный размер набора не гарантирует быстрый успешный ответ.

**Без источника привлекательности остановки от 12 часов будут отсеяны.**
Нулевая оценка — неизвестность, а не оценка качества города. Отсутствующая стоимость
визы остаётся неизвестной по правилам MVP. Топология эти зависимости не заменяет.

## Проверки разработки

```shell
uv run --locked python -m unittest discover -s tests -p test_topology.py -v
```

Регрессии проверяют откат транзакции, сохранение профилей, независимость направлений,
ошибки/отмену источника, границы покрытия. Условие отбора сравнивается с полным
перебором маршрутов на 50 случайных графах; итоговая выдача планировщика с SQLite —
с независимым перебором комбинаций билетов. CI по-прежнему только Ruff и mypy.
