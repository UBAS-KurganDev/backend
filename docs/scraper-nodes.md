# Скрапер-ноды: параллельный сбор билетов

Прототип ускоряет сбор за счёт нескольких независимых процессов-нод. Каждая
нода держит собственный Chromium и выполняет реальный поиск agent.ru. Worker
раскладывает пары аэропортов одного города по нодам параллельно. Контракт
`FlightProvider`, результат версии 2 и правила полноты не меняются.

Это не production-HA: нет service discovery, health-check, circuit breaker,
mTLS и распределённого single-flight. Ноды обязаны быть одной версии с worker,
потому что обмениваются внутренним JSON `CapturedOffers` версии 2.

## Схема

```text
RoutePlanner
  -> AgentFlightProvider             города -> пары аэропортов
  -> NodeSearchService               кэш и single-flight координатора
  -> NodePool                        выбор наименее загруженной ноды
  -> POST /v1/search                 параллельно на N нод
  -> FlightSearchService ноды        локальный кэш, повторы, лимит браузеров
  -> Chromium -> agent.ru
```

Одна пара `аэропорт отправления -> аэропорт назначения` уходит ровно на одну
ноду. Разные пары распределяются одновременно. Если `UBAS_AGENT_NODE_URLS`
пуст, используется прежний in-process скрапер.

Нода не знает о городах, маршрутах и ценах: она возвращает исходный захват
страниц. Нормализация, проверка даты, отсев классов и дедупликация по-прежнему
выполняются в worker общим кодом `mapping.py`. Поэтому распределение не меняет
семантику `complete`, `warnings` и `fetched_at`: время первого ответа источника
приходит с ноды и не обновляется при чтении кэша.

## HTTP-контракт ноды

| Метод и путь | Назначение |
| --- | --- |
| `POST /v1/search` | `SearchRequest` -> `CapturedOffers` версии 2 |
| `GET /healthz` | `{"status":"ok"}` без проверки источника |

Тело запроса:

```json
{"origin": "SVX", "destination": "AYT", "depart_date": "2027-01-15"}
```

Успех — только полный `Ready`-захват. Ошибки:

| Ответ | Смысл | Действие координатора |
| --- | --- | --- |
| 200 | полный захват | разобрать и закэшировать |
| 401 | неверный `X-UBAS-Node-Token` | окончательная ошибка |
| 422 | источник отклонил пару/дату или неверный формат | окончательная ошибка |
| 503 | временная ошибка Chromium/HTTP 429/5xx | повтор на другой ноде |

Клиент проверяет JSON ноды той же Pydantic-моделью. Неверный или неполный
payload — окончательная `FlightProviderError`, а не пустая успешная выдача.

## Настройки

Нода читает обычные `UBAS_AGENT_*`:

- `UBAS_AGENT_MAX_CONCURRENCY` — одновременных браузеров на ноде;
- `UBAS_AGENT_TIMEOUT_SECONDS`, `UBAS_AGENT_MAX_ATTEMPTS`,
  `UBAS_AGENT_MAX_RESPONSE_BATCHES` — бюджет одного захвата;
- `UBAS_AGENT_CACHE_*` — локальный кэш ноды;
- `UBAS_AGENT_NODE_HOST`, `UBAS_AGENT_NODE_PORT` — адрес по умолчанию,
  `--host`/`--port` их переопределяют.

Worker дополнительно читает:

| Переменная | Смысл |
| --- | --- |
| `UBAS_AGENT_NODE_URLS` | origins через запятую; пусто — локальный скрапер |
| `UBAS_AGENT_NODE_CONCURRENCY` | слотов на ноду; согласуйте с её `MAX_CONCURRENCY` |
| `UBAS_AGENT_NODE_TIMEOUT_SECONDS` | таймаут HTTP-вызова одной пары, по умолчанию 150 |
| `UBAS_AGENT_NODE_MAX_ATTEMPTS` | попыток с переключением ноды при 503/сети |
| `UBAS_AGENT_NODE_TOKEN` | необязательный общий секрет для заголовка |

Суммарная параллельность координатора равна
`число_нод * NODE_CONCURRENCY`. Планировщик по-прежнему ограничивает число
одновременных городских запросов `max_concurrent_queries`, а бюджет одного
городского запроса остаётся 150 секундам из `config/planner.json`. Увеличение
числа нод не расширяет этот бюджет: медленная или мёртвая нода съедает попытки.

## Запуск двух нод локально

Установите Chromium один раз:

```shell
uv run --locked playwright install chromium
```

В двух терминалах (одинаковый `.env`, разные порты):

```shell
uv run --env-file .env ubas-scraper-node --port 8101
uv run --env-file .env ubas-scraper-node --port 8102
```

В `.env` worker укажите те же ноды:

```dotenv
UBAS_AGENT_NODE_URLS=http://127.0.0.1:8101,http://127.0.0.1:8102
UBAS_AGENT_NODE_CONCURRENCY=2
```

Затем обычный worker:

```shell
uv run --env-file .env ubas-worker
```

Проверка доступности: `GET http://127.0.0.1:8101/healthz` и
`http://127.0.0.1:8102/healthz`. Для отдельной диагностики одной пары можно
вызвать ручку напрямую с телом `SearchRequest`.

Ноды слушают `127.0.0.1` по умолчанию. Не выставляйте ручку в интернет без
TLS, аутентификации и сетевой изоляции. `UBAS_AGENT_NODE_TOKEN` — только общий
секрет, не авторизация пользователей.

## VM в Yandex Cloud через Terraform

Для прототипа есть отдельный Terraform-модуль
[deployment/terraform/scraper-node](../deployment/terraform/scraper-node/README.md).
Одна команда создаёт VPC, subnet, security group, service account, VM и запускает
контейнер ноды через cloud-init, затем ждёт `/healthz`:

```shell
./deployment/terraform/scraper-node/apply.sh
```

`TF_VAR_node_count=2 ./deployment/terraform/scraper-node/apply.sh` поднимает две VM;
`terraform output -raw worker_env` печатает значения `UBAS_AGENT_NODE_*`.
Модуль создаёт отдельную инфраструктуру и не меняет production VM `ubas-backend`.
По умолчанию порт ноды открыт в интернет и защищён сгенерированным токеном;
ограничьте `node_allowed_cidrs` сетью worker'а. Токен хранится в Terraform state
и в metadata VM, поэтому state нельзя коммитить.

## Замер скорости

Скрипт запускает две настоящие локальные HTTP-ноды с детерминированной
задержкой вместо agent.ru и прогоняет один и тот же путь `AgentFlightProvider`
для MOW -> TYO (8 пар аэропортов, по 2 браузерных слота на ноду):

```shell
uv run --locked python scripts/benchmark_scraper_nodes.py --runs 3 --delay 0.5
```

Пример результата на локальной машине:

```text
1 узел:  median=2.025s min=2.024s max=2.036s
2 узла:  median=1.025s min=1.019s max=1.026s
Ускорение по медиане: 1.98x
```

Это замер самого прототипа: сетевой fan-out, семафоры и кэш участвуют, а
задержка источника фиксирована. В реальном поиске выигрыш ограничен числом
пар аэропортов, слотами каждой ноды, скоростью agent.ru и его лимитами.
Ноды не обходят ограничения источника; рост параллельности может привести к
429 и повторам.

Живой замер по уже запущенным нодам:

```shell
uv run --locked python scripts/benchmark_scraper_nodes.py \
  --nodes http://127.0.0.1:8101,http://127.0.0.1:8102 --runs 3
```

Сценарии используют разные даты, чтобы не сравнивать кэш с сетью. Выдача
agent.ru меняется между датами, поэтому это ориентир по времени, а не
контролируемый ценовой эксперимент.

## Границы прототипа

- Нет проверки живости перед выбором ноды: недоступная нода стоит одну
  неудачную попытку, затем запрос уходит на следующую.
- Нет ограничения очереди на ноде сверх HTTP-таймаута и семафора браузеров.
- Кэш координатора и нод не заменяет распределённый single-flight. Redis, если
  задан, разделяет готовые захваты, но не арендует вычисление между worker'ами.
- Ноды должны использовать совместимую версию `CapturedOffers`; старый payload
  не декодируется как успешный.
- Ошибка любой пары при завершённом поиске по-прежнему делает весь городской
  запрос неуспешным: частичные карточки не публикуются.
