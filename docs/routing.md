# Планировщик MVP: контракт и настройки

Реальный адаптер agent.ru, формат источника и ограничения покрытия описаны
в [agent-scraper.md](agent-scraper.md).

Источник требований — [MVP](https://github.com/UBAS-KurganDev/docs/blob/d4d838879c6e054bd4acac22e2678dbfc8c8cf1a/mvp.md)
и [критерии приёмки](https://github.com/UBAS-KurganDev/docs/blob/d4d838879c6e054bd4acac22e2678dbfc8c8cf1a/Критерии%20приёмки%20MVP.md).
Уточнение владельца от 2026-11-06: теперь максимум одна остановка; это явное
изменение прежнего требования до трёх остановок. Остальные требования сохраняются.
По решению владельца проекта временный порог привлекательности — **60 из 100**.
Дополнительно согласован ограниченный охват: до 30 промежуточных городов по
привлекательности, при равенстве — по связности. Это явное уточнение прежней
полноты поиска; результат оптимален внутри выбранного набора запросов, а не
обязательно во всей топологии. Детали и search_scope — в planner-search.md
и direct-routes.md. Кэш не является условием корректности или успешного завершения.

## Вход и выдача

HTTP принимает только origin, destination, date_from, date_to.
Коды обозначают города IATA, а не аэропорты. Один взрослый, экономкласс,
гражданство РФ, обычный загранпаспорт без иностранных виз и ВНЖ.
Окно — до 30 календарных дней включительно. Начало может совпадать с сегодняшней
датой в исходном городе. API использует отдельный источник географии для
проверки местной даты до помещения запроса в очередь.

Допустимы прямой маршрут и одна остановка, единые и отдельные билеты.
Вылет и конечное прибытие проверяются по местным датам соответствующих аэропортов.
Между соседними рейсами в одном аэропорту достаточно любого строго положительного
интервала. При смене аэропорта в том же городе требуется минимум два часа между
прилётом и следующим вылетом. Интервал считается в UTC; локальное отображение
использует IANA timezone конкретного аэропорта. Нет лимита 72 часа, требования
дневного времени или выхода в город. Смена аэропорта отмечается предупреждением.

Остановка от 12 часов включительно требует оценки города >= tourism_threshold.
Правило проверяется для каждой остановки, включая остановки внутри единого билета.
Отсутствие ответа источника привлекательности даёт оценку 0. Остановки короче
12 часов и прямые рейсы не требуют положительной оценки.

Результат — максимум 10 предложений, отсортированных только по сумме известных
расходов в RUB. Дубли сохраняются. Квот городов и прямых рейсов нет; порядок
равных цен произвольный. Стоимость отелей, переездов и дополнительного багажа
не добавляется. Рейтинг «крутости» и проверки права въезда удалены.

## Контракт источника билетов

FlightProvider.search(FlightQuery) — отменяемый async-вызов. Запрос содержит:

| Поле | Смысл |
| --- | --- |
| origin, destination | Города; охватить все относящиеся к ним аэропорты |
| departure_date | Одна местная дата первого вылета билета |
| max_segments | Максимум рейсов в одном билете, до 4 |
| passengers | Всегда 1 |
| currency | Желаемая валюта RUB; исходная валюта цены сохраняется |
| limit | Максимум предложений одного ответа |

Старые stopover_city и max_stopover_hours удалены. Один запрос пары городов
включает как прямые, так и единые билеты с остановками. Планнер перебирает даты; адаптер внутри дня перебирает страницы и аэропорты.
Неполная выдача за день означает complete=false и незавершённый поиск.

FlightSearchResult содержит offers, complete, warnings.
complete=true означает полный ответ в согласованной области данного запроса.
Обрезка, неполная пагинация или неподдерживаемая часть запроса требуют false.
Ожидаемые сетевые ошибки переводятся в FlightProviderError.
Пустой полный ответ — успешный поиск без предложений.

TicketOffer — **один самостоятельно покупаемый билет**:

- provider и offer_id идентифицируют предложение источника.
- segments — 1–4 последовательных рейса; цена относится ко всему билету.
- total_price — известная сумма с обязательными сборами в исходной валюте;
  null, если сумма неизвестна. unknown_costs перечисляет неизвестные обязательные
  дополнения к известной сумме. Нельзя выдавать цену одного сегмента за цену билета.
- Тариф — минимальный доступный эконом для одного взрослого. Это обязанность
  адаптера источника; планировщик не может восстановить неотданные тарифы.
- baggage_description передаёт условия багажа; checked_baggage_included —
  совместимый дополнительный признак. Неизвестные условия не выдумываются.
- fetched_at — реальное время получения цены, неизменное при чтении кэша.
  expires_at необязателен и сохраняется как информация источника. Политика
  допустимого возраста ещё не согласована (OPEN-07); принудительной перепроверки нет.
- У каждого рейса обязательны авиакомпания, номер, аэропорты, aware datetime
  и IANA timezone аэропортов. Сравнение времени происходит в UTC.
- protected_connection остаётся справочным полем и не влияет на цену/отбор.
  booking_url не публикуется: ссылки на покупку вне MVP.

Нельзя разбивать единый билет на якобы продаваемые отдельно сегменты.
Дубли внутри ответа сохраняются. Перекрывающиеся транспортные ответы при
уточнении дат заменяются, а не складываются: алгоритм не создаёт искусственные дубли.

## Деньги и визовые расходы

CostCalculator переводит каждый известный компонент в RUB по rub_rates.
Используются Decimal и округление каждого компонента до копеек ROUND_HALF_UP.
Это явная временная техническая политика: внешний источник курса и окончательные
правила округления остаются OPEN-04. По умолчанию известен только RUB=1.
Нет курса — компонент неизвестен, исходная сумма и валюта сохраняются.

VisaCostResolver.expenses получает весь маршрут и возвращает необходимые
визовые расходы с уникальными ключами. Благодаря этому будущий источник может
учесть повторное посещение страны или одну визу для нескольких остановок.
Неизвестный расход не исключает маршрут и не штрафует его при сортировке.

Стандартный CatalogVisaCosts использует справочную цену RU-визы первого
промежуточного посещения страны. Для повторного посещения добавляет неизвестный
компонент repeat_country_rules_unknown; не предполагает, что первая виза
покрывает повторный въезд. Нет профиля/цены — required_visa_cost_unknown.
Промежуточное посещение России не создаёт визового компонента: профиль MVP
фиксирует гражданство RU.
Это временный консервативный адаптер: правила определения необходимых расходов,
включая конечную страну, требуют отдельного согласования OPEN-06.
Он не выводит расходы конечной страны из транзитных профилей; у прямого рейса
по умолчанию нет пересадочной визы. Источник стоимости заменяется обычным
аргументом visa_costs при создании RoutePlanner.

Поля status, processing_days, max_stay_hours, verified_at/valid_until старых
визовых профилей не используются для проверки возможности поездки.
Калибровка актуальности визовых цен относится к будущему источнику расходов.

## Конфигурация

JSON через UBAS_PLANNER_CONFIG_PATH одинаков для API и worker:

```json
{
  "tourism_threshold": 60,
  "rub_rates": {"RUB": "1", "USD": "90"},
  "max_hubs": 30,
  "max_topology_cities": 2000,
  "max_topology_edges": 100000,
  "max_offers_per_query": 200,
  "max_offers_per_search": 2000,
  "max_total_offers": 50000,
  "max_provider_queries": 4000,
  "max_search_nodes": 200000,
  "max_frontier": 200000,
  "max_candidates": 100000,
  "max_concurrent_queries": 8,
  "query_timeout_seconds": 30,
  "search_timeout_seconds": 1200
}
```

USD=90 выше — пример, не реальный курс. Старые веса, квоты и буферы больше
не принимаются: неверная конфигурация завершается понятной ошибкой Pydantic.
Лимиты времени — защитные настройки прототипа, не согласованный SLA.

Успешный PlanResult версии 2 всегда complete=true. Если не удалось доказать
полноту поиска в выбранном покрытии, планировщик поднимает IncompleteSearchError.
Worker сохраняет failed/search_incomplete без карточек. Это временная политика
обработки OPEN-05; успешное отсутствие маршрутов имеет completed с пустым routes.

Подробности алгоритма — [planner-search.md](planner-search.md), изменения
ответа для фронта — [direct-routes.md](direct-routes.md).

## Источник привлекательности

Офлайн-импорт OpenTripMap и временная фиксированная калибровка 0–100 описаны
в [tourism-import.md](tourism-import.md). Импорт не меняет правила ранжирования
маршрутов или визовые расходы. Старые относительные оценки снимка пересчитываются
из счётчиков достопримечательностей; в планнер передаётся `CityProfile` версии 2.

## Переход на запросы по одной дате

Внутренний `FlightQuery` теперь принимает `departure_date`; `departure_from` и
`departure_to` удалены. Сторонние провайдеры нужно обновить вместе с worker.
Удалите `refine_date_ranges` из пользовательских PlannerConfig JSON: неизвестная
настройка отклоняется при загрузке. HTTP-ввод с двумя датами и формат сохранённых
результатов не меняются, миграция БД не нужна. Лимиты вызовов не увеличены.
