# Планировщик маршрутов

## Контракт поиска билетов

`FlightProvider.search(FlightQuery) -> FlightSearchResult` — асинхронный порт
в `routing/ports.py`. HTTP/SDK-адаптер провайдера нужно реализовать отдельно.
Модели в `routing/schemas.py` валидируются Pydantic, поддерживают
`model_validate_json`, `model_dump_json` и `model_json_schema`.

Запрос передаёт города IATA (например, MOW, а не аэропорт SVO), диапазон **местных
дат вылета**, число взрослых пассажиров, валюту и лимит предложений.
`stopover_city=null` запрашивает только прямой рейс; указанный город — единое
покупаемое предложение ровно с двумя сегментами через этот город.
`max_stopover_hours` ограничивает остановку. Дополнительные пересадки в MVP не поддержаны.

Ответ сервиса:

```json
{
  "offers": [{
    "provider": "example",
    "offer_id": "quote-123",
    "segments": [{
      "origin": {"code": "SVO", "city_code": "MOW", "timezone": "Europe/Moscow"},
      "destination": {"code": "ALA", "city_code": "ALA", "timezone": "Asia/Almaty"},
      "departure_at": "2027-06-01T09:00:00+03:00",
      "arrival_at": "2027-06-01T15:00:00+05:00",
      "marketing_carrier": "XX",
      "operating_carrier": "XX",
      "flight_number": "101"
    }],
    "total_price": {"amount": "12000.00", "currency": "RUB"},
    "passengers": 1,
    "cabin": "economy",
    "checked_baggage_included": true,
    "protected_connection": false,
    "booking_url": "https://example.com/offers/quote-123",
    "fetched_at": "2027-05-01T12:00:00Z",
    "expires_at": "2027-05-01T12:20:00Z"
  }],
  "complete": true,
  "warnings": []
}
```

Все данные примера вымышлены. `total_price` — конечная стоимость **всех пассажиров**
с обязательными сборами, в валюте запроса. Деньги передаются десятичными строками.
Конвертацию выполняет адаптер; смешанные валюты не суммируются. Багаж: `true` —
включён для всех пассажиров на всех сегментах, `false` — нет, `null` — неизвестно.
`protected_connection` означает подтверждённую защиту стыковки перевозчиком;
одна покупка сама по себе её не гарантирует. У разных билетов защиты нет.
Время обязательно содержит UTC-смещение, аэропорт — IANA timezone.
`offer_id` уникален внутри провайдера для конкретного предложения.

Если провайдер обрезал выдачу, не закончил пагинацию или не поддерживает единые
билеты через указанный город, он возвращает `complete=false` и пояснение в `warnings`.
Ожидаемые сетевые ошибки адаптер переводит в `FlightProviderError`.
Пустой полный ответ означает, что предложений действительно не найдено.

## Поиск и ранжирование

1. Пересечение исходящих связей A и входящих связей C даёт города B.
2. Отбрасываются исключённые/неинтересные города и неподходящие визовые данные.
   При лимите городов предпочтение отдаётся туристической оценке.
3. Для каждого B параллельно запрашиваются A→B, B→C и единый A→B→C.
   Семафор ограничивает нагрузку; каждый вызов имеет таймаут.
4. Бинарный поиск по времени вылета B→C подбирает пары в допустимом окне.
   Единые и отдельные билеты перебираются поочерёдно; города — по кругу.
5. Проверяются даты, бюджет, въездная виза, длительность остановки, багаж,
   смена аэропорта и полезное дневное время после аэропортовых запасов.
6. Вычисляется рейтинг, удаляются дубликаты одинаковых рейсов и условий,
   применяется лимит вариантов на город и общий top-N.

`RouteRequest.date_from/date_to` включительно ограничивают **и вылет из A,
и прибытие в C** по местным календарям соответствующих аэропортов.
Пока поддержаны взрослые пассажиры и одна остановка. Максимум по умолчанию — 72 часа.
Часовые интервалы считаются в UTC, местные окна — с учётом IANA/DST.

«День» — настраиваемое окно туристической активности, по умолчанию 08:00–22:00,
а не астрономический световой день. Из остановки вычитаются 2 часа после прилёта,
2 часа до вылета, ещё 1 час для отдельных/незащищённых билетов и 2 часа при смене
аэропорта. В оставшемся времени доля дня должна быть **строго больше 0.5**,
а дневных часов — не меньше 3 и городского `minimum_visit_hours`.
`DaytimeCalculator` можно заменить расчётом восхода/заката или расписаниями мест.

`total_cost = сумма цен билетов + fee_per_person × passengers`.
Отель и наземный транспорт в стоимость и рейтинг не включены; цена отеля остаётся
справочным полем профиля. Пограничные/визовые сведения должны разрешать **выход
в город**, а не только транзит. Неизвестные, устаревшие и недоступные условия исключаются;
проверяются срок оформления и разрешённая длительность пребывания.
Допуск в конечную страну и личные исключения по визам пока не проверяются.

Формула: `score = 100 × Σ(weight × utility) / Σ(weight)`.
Каждая utility лежит в [0, 1]; вклад каждого фактора возвращается в `score.components`.

| Фактор | Вес | Utility |
| --- | ---: | --- |
| Цена с визой | 0.40 | `1 / (1 + price / price_references[currency])` |
| Туризм | 0.25 | привлекательность × достаточность дневных часов × штраф за слишком долгий визит |
| Дневное время | 0.15 | доля дня × `min(daytime_hours / target_daytime_hours, 1)` |
| Удобство визы | 0.10 | `visa.ease` |
| Общая длительность | 0.05 | `1 / (1 + trip_hours / duration_reference_hours)` |
| Защита стыковки | 0.05 | `max(0, 1 − self_transfer_penalty − airport_change_penalty)` для применимых рисков |

Туризм: `tourism_score × min(daytime / target, 1) × min(rewarding_visit_hours / daytime, 1)`.
Так профиль отвечает на вопрос, сколько времени в городе есть чем заняться.
Штрафы за риск — параметры предпочтений, не статистические вероятности.
Нормализация использует постоянные масштабы, поэтому добавление постороннего
предложения не меняет оценки уже найденных маршрутов.

## Настройки и расширение

`PlannerConfig` задаёт веса, масштабы цены/времени, аэропортовые запасы,
число результатов на город, фильтры и ограничения нагрузки.
`price_references` хранит масштаб цены для каждой поддерживаемой валюты
для всей группы пассажиров. По умолчанию задано `{"RUB": 60000}`.
API отклоняет валюту без настроенного масштаба с HTTP 422 до постановки в очередь.
Для нескольких валют задайте эквивалентные масштабы; курсы автоматически не загружаются.
Провайдер и визовые данные каталога также должны поддерживать валюту запроса.
Пример изменения через JSON:

```python
from ubas_backend.routing.config import PlannerConfig

config = PlannerConfig.model_validate_json("""{
  "price_references": {"RUB": 60000},
  "weights": {"price": 0.6, "tourism": 0.3, "protection": 0.1,
              "daytime": 0, "visa": 0, "duration": 0},
  "max_hubs": 30,
  "max_stopover_hours": 48,
  "allow_airport_change": false
}""")
```

Непереданные параметры сохраняют значения по умолчанию. Передавайте `config`
конструктору `RoutePlanner`. Его зависимости — `FlightProvider`,
`TopologyRepository`, `CityRepository`, `RouteScorer` и `DaytimeCalculator`.
Топология и профили могут жить в разных БД. Новые способы оценки подключаются
через `RouteScorer`, транспорт API можно добавить поверх `plan()`.

Для запущенного приложения укажите `UBAS_PLANNER_CONFIG_PATH` — путь к JSON
с настройками. API и worker должны читать одинаковую конфигурацию, поскольку
диапазон дат и допустимые валюты проверяются до создания задачи и перед расчётом.
`FlightProvider` может реализовать `async aclose()` для закрытия своего HTTP-клиента;
runtime вызовет его при завершении процесса.

Планирование разделено на модули:

- `policy.py` — ограничения входного запроса и выбор визовой политики;
- `hubs.py` — отбор городов по топологии и справочникам;
- `offers.py` — запросы провайдеру, ограничения параллелизма, сочетания билетов;
- `validation.py` — чистые проверки предложения, возвращающие причину отказа;
- `candidates.py` — построение маршрута, стоимость и полезное время;
- `scoring.py` — рейтинг; `selection.py` — top-N и разнообразие городов;
- `planner.py` — координация шагов; `diagnostics.py` — статистика одного поиска.

Запросы к провайдеру объединены в `TaskGroup`: отмена расчёта или неожиданная
ошибка отменяет дочерние поиски. Лимит конкурентных обращений общий для одного
экземпляра планировщика. При переборе кандидатов управление регулярно отдаётся
event loop, чтобы продление аренды и отмена не ждали окончания всего перебора.

`SqliteCatalog` использует SQLAlchemy ORM и реализует оба репозитория:
индексированные направленные связи
`flight_links` и валидируемые JSON-профили `city_profiles`. `initialize()` создаёт
схему; `upsert(CatalogData(...))` загружает данные. Асинхронные чтения выполняются
в рабочих потоках. Каталог не поставляет мировые данные: нужен отдельный импортёр
реальных связей, туристических оценок и проверенных визовых правил. Связь в графе
означает возможное направление; наличие рейса на нужную дату проверяет провайдер.

`complete=false` обозначает ошибки провайдера, отсутствующие профили или достижение
лимитов поиска; `warnings` объясняет причину. `rejected` содержит счётчики причин
отсева, `evaluated_candidates` — число рассмотренных комбинаций. Это эвристический
top-N среди рассмотренных предложений, без гарантии глобального минимума цены.
`complete=true` означает завершение поиска в заданной топологии и фильтрах.

## Запуск примера

```shell
uv sync --locked
uv run python -m ubas_backend.routing.demo
```

Пример создаёт временную SQLite-базу, подставляет вымышленные цены и визовые правила
и выводит JSON с двумя вариантами через Алматы. Даты формируются относительно
момента запуска. Внешние сервисы и реальные визовые сведения не используются.
