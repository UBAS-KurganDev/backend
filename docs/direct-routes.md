# Контракт результата для фронта: MVP, версия 2

## Запрос

POST /api/v1/queries принимает только четыре поля:

```json
{
  "origin": "MOW",
  "destination": "TYO",
  "date_from": "2027-06-01",
  "date_to": "2027-06-30"
}
```

Старые поля passengers, citizenship, currency, budget, limit, excluded_cities,
checked_baggage_required из HTTP удалены. Передача лишнего поля даёт 422.
Фиксированы один взрослый, эконом, РФ, RUB и максимум 10 результатов.

Три ручки и состояния очереди сохранены: POST возвращает 202 с query_id;
клиент ждёт completed через GET /{id}, затем получает GET /{id}/result.
Промежуточных карточек нет. Это ожидание полного поиска в смысле FLOW-01/02;
транспорт остаётся асинхронным с polling, а не одним долгим HTTP-запросом.
Если требуется буквально синхронный HTTP, это отдельное изменение транспорта.

## Результат

Оболочка: {query_id, result}. У result есть schema_version=2 и routes.
Каждый элемент routes сохраняет оболочку {route, score}; score=null,
использовать его для сортировки нельзя. Порядок уже задан бэкендом только по
route.total_cost.amount. Деньги — десятичные строки, итоговая валюта RUB.

| Поле route | Смысл |
| --- | --- |
| kind | direct для одного рейса, stopover для 2–4 рейсов |
| tickets | Покупаемые билеты; каждый содержит свои рейсы и одну общую цену |
| stopovers | Массив 0–3 остановок, включая остановки внутри единого билета |
| costs | Компоненты стоимости: key, kind, original, rub_amount, unknown_reason |
| ticket_cost, visa_cost | Суммы известных компонентов соответствующего вида в RUB |
| total_cost | Сумма известных билетов и виз, без штрафа за неизвестные компоненты |
| full_cost_known | false, если хотя бы один обязательный компонент неизвестен |
| unknown_costs | Ключи неизвестных компонентов из costs |
| total_trip_hours | Полное время от первого вылета до конечного прибытия |
| warnings | Предупреждения об исключённых расходах, смене аэропорта, багаже |

При full_cost_known=false показывать «Полная стоимость неизвестна» и перечислить
неизвестные компоненты. Ноль в рассчитанной сумме не означает бесплатный билет
или визу. Для каждого билета показывать total_price целиком, а не умножать его
на число рейсов. fetched_at — время фактического получения цены, не время ответа API.

Stopover содержит city_code, arrival_airport, departure_airport, arrival_at,
departure_at, duration_hours, tourism_score (0–100), airport_change, self_transfer.
Предупреждать о каждой смене аэропорта. Интервал — время между рейсами без
вычитания переезда или аэропортовых процедур.

Локальные даты для карточек получаются из aware datetime и IANA timezone
соответствующего аэропорта. Время входных данных может быть задано в UTC.
Показывать условия baggage_description либо checked_baggage_included;
неизвестность не заменять утверждением об отсутствии багажа.
Проживание и переезды в цену не входят. Ссылки на покупку не возвращаются.

Для прямого рейса stopovers=[], visa_cost=0 у стандартного адаптера, нет
вымышленного города/визы. Квоты прямых рейсов нет: все десять могут быть прямыми.
Дубли сохраняются; у карточек разные id даже при одинаковых рейсах.

## Ошибки и совместимость

Новый успешный результат всегда complete=true. Незавершённый поиск даёт
failed с failure.code=search_incomplete; /result возвращает 409.
Такой ответ не показывать как «Маршруты не найдены». Только completed с пустым
routes означает успешный поиск без вариантов. Повторный поиск — новый ключ.

Старые сохранённые результаты читаются с schema_version=1, без пересчёта.
Поля stopover, visa, metrics и score оставлены в моделях для их чтения;
в новых результатах они null. Фронту нужны отдельные ветки отображения
версий 1 и 2. Исторические complete=false и старый рейтинг не являются
результатами нового MVP.

Схема PostgreSQL не меняется, UUID/ключи/JSON не перезаписываются. Старые
сохранённые запросы по-прежнему декодируются. Если в ожидающем запросе есть
опции вне MVP, worker завершит его invalid_request без повторов.
Перед обновлением остановить API и worker, заменить конфигурацию планировщика
и развернуть их одной версией. Для старых ключей с нестандартными опциями
сохранённый результат доступен через прежний UUID; новые запросы используют
новый четырёхполевой контракт.
