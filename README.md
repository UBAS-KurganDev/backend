# UBAS Backend

Python-бэкенд UBAS: подбор маршрутов с туристической остановкой до 3 дней.
Исходный код расположен в `src/ubas_backend`.

Планировщик сравнивает единые и отдельные билеты, учитывает стоимость въездной визы,
дневное время для прогулок, привлекательность города и риск стыковки.
Есть SQLite-каталог топологии/городов и заменяемые интерфейсы провайдера и рейтинга.
HTTP API создаёт долговечные запросы маршрутов в PostgreSQL; worker выполняет их
через планировщик. Реальный поставщик билетов подключается отдельным адаптером.

```shell
uv sync --locked
uv run python -m ubas_backend.routing.demo
```

Пример использует только вымышленные данные. Документация:

- [контракт билетов, настройки и запуск](docs/routing.md);
- [устройство, логика работы и алгоритмы](docs/architecture.md).

Правила разработки и карта проекта для агентов — в [AGENTS.md](AGENTS.md).

## Запуск API и worker

После `uv sync --locked` заполните переменные окружения по [.env.example](.env.example),
создайте PostgreSQL-базу и примените миграцию:

```shell
uv run ubas-migrate
```

Если настройки лежат в `.env`, используйте `uv run --env-file .env ubas-migrate`
(аналогично для `ubas-api` и `ubas-worker`): приложение само `.env` не читает.
Переход со старой SQL-миграции выполняется автоматически с сохранением задач,
результатов и существующих ключей. Перед обновлением остановите старые API/worker,
после миграции запустите новую версию.

Затем запустите API и worker в разных терминалах:

```shell
uv run ubas-api
uv run ubas-worker
```

API будет доступен на `http://127.0.0.1:8000`, интерактивная документация — на
`http://127.0.0.1:8000/docs`. Подробнее о состояниях, атомарности и настройке
worker — в [документации QueryManager](docs/query-manager.md).

Для локальной разработки с worker внутри API задайте
`UBAS_EMBEDDED_WORKER=true` и запустите:

```shell
uv run uvicorn ubas_backend.main:app --reload
```

## Запуск через Docker Compose

Нужны Docker Engine и Docker Compose. Подготовьте `.env` из `.env.example`
(если своего `.env` ещё нет), задайте непустой `POSTGRES_PASSWORD` и запустите:

```shell
mkdir -p var
docker compose up --build -d
docker compose ps
```

По умолчанию запускаются два контейнера: `postgres` и `api`. PostgreSQL создаёт
пользователя и базу из `POSTGRES_USER` / `POSTGRES_DB`, затем API применяет миграции
и начинает принимать запросы. Документация доступна на
`http://127.0.0.1:8000/docs`; порт хоста меняется через `UBAS_HTTP_PORT`.
Compose использует имя проекта `ubas-backend`, чтобы ресурсы не пересекались
с другими проектами в папках `backend`. Данные PostgreSQL сохраняются в volume
`ubas-backend_postgres_data`.

Compose собирает внутренний URL подключения к `postgres:5432` из `POSTGRES_*`;
`UBAS_DATABASE_URL` из `.env` остаётся настройкой для локальных команд `uv`.
Порт PostgreSQL на хост не публикуется. SQLite-каталог и необязательный JSON
планировщика размещайте в `./var`: этот каталог монтируется в `/app/var` для чтения.

Для обработки запросов нужен worker, существующий SQLite-каталог и реализация
провайдера билетов в образе. После настройки `UBAS_FLIGHT_PROVIDER_FACTORY`:

```shell
docker compose --profile worker up --build -d
```

Это добавляет третий контейнер `worker`. Без него API сохраняет запросы в очередь,
но не выполняет поиск. Значение фабрики из `.env.example` — шаблон; реальный
адаптер не поставляется. Каталог, созданный из демо, содержит вымышленные сведения.

Для проверки всей системы сначала создайте отдельный демонстрационный каталог:

```shell
uv run --locked python -m ubas_backend.routing.demo --catalog ./var/demo-catalog.sqlite3
```

Если на хосте установлен только Docker, эту команду можно выполнить в образе
без запуска БД и миграций (для записи в bind mount используется root):

```shell
docker compose run --rm --no-deps --build --user 0:0 --volume ./var:/app/var:rw api python -m ubas_backend.routing.demo --catalog ./var/demo-catalog.sqlite3
```

Затем задайте в `.env`:

```dotenv
UBAS_FLIGHT_PROVIDER_FACTORY=ubas_backend.routing.demo:create_flight_provider
UBAS_CATALOG_PATH=./var/demo-catalog.sqlite3
COMPOSE_PROFILES=worker
```

Затем выполните `docker compose up --build -d`. Будут запущены PostgreSQL,
API и worker. `python3 scripts/query_route.py` без аргументов отправит запрос,
для которого демо-провайдер возвращает два маршрута через Алматы: отдельные
билеты за 36000 RUB и единый за 42000 RUB. Это полностью вымышленные цены
и визовые сведения. Предложения рассчитаны на одного пассажира, RUB и вылет
через 14 дней от текущей даты UTC; другие параметры могут дать пустой результат.
Срок действия предложений обновляется при каждом обращении, а в ответе есть
предупреждение `synthetic_demo_data`. Запись результата в очереди не обновляет
сохранённые предложения: новый поиск после завершения создаётся с новым ключом.

Каталог генерируется с визовыми датами от момента запуска команды на 90 дней.
Перед повторной демонстрацией остановите worker и повторите команду подготовки
с `--overwrite`, затем запустите worker. Это заменит выбранный файл целиком;
используйте только отдельный демо-каталог. Без флага существующий файл не меняется.
Worker не обновляет визовые сведения автоматически. SQLite-каталоги не хранятся
в Git; `var/demo-result.json` — исторический пример ответа, а не актуальные билеты.

Логи и остановка с сохранением данных:

```shell
docker compose logs -f api
docker compose --profile worker down
```

Перед обновлением образа остановите существующие API и worker через `down`,
затем выполните `up --build -d` с нужным профилем. Так миграции не пересекаются
с работой предыдущей версии. Не добавляйте `--volumes` к `down`, если нужно
сохранить PostgreSQL. Подробнее — [подключение БД и контейнеры](docs/query-manager.md#docker-compose).

## Отправка запроса из Python

Скрипт [scripts/query_route.py](scripts/query_route.py) использует стандартную
библиотеку Python и запускается на хосте, где опубликован порт API:

```shell
python3 scripts/query_route.py
```

По умолчанию отправляется запрос `MOW → TYO` с вылетом и конечным прибытием
в период от текущей даты UTC + 14 дней до этой даты + 3 дня, для одного пассажира,
в RUB. Скрипт выводит номер запроса (`query_id`), опрашивает его состояние
и печатает JSON ответа `/result`. Это идентификатор поиска, а не бронирования.

Параметры можно изменить:

```shell
python3 scripts/query_route.py --origin MOW --destination TYO \
  --date-from 2027-06-01 --date-to 2027-06-04 --budget 100000 \
  --timeout 600
```

Адрес по умолчанию — `http://127.0.0.1:8000`. Если `UBAS_HTTP_PORT` изменён,
передайте `--base-url http://127.0.0.1:НОВЫЙ_ПОРТ`: скрипт не читает `.env`.
Коды должны обозначать города, а не аэропорты. Все параметры перечислены в `--help`.

Номер запроса, ключ идемпотентности и изменения статуса выводятся в stderr,
а JSON бэкенда — в stdout, поэтому результат можно сохранить:

```shell
python3 scripts/query_route.py > result.json
```

По умолчанию ожидание ограничено 600 секундами. При таймауте, ошибке API или
ошибке задачи скрипт завершается с кодом 1; при успешном результате — с кодом 0.
`complete=false` означает частичный результат и не меняет успешный код выхода.
После таймаута или прерывания можно продолжить ожидание, передав
`--query-id UUID_ПРЕЖНЕГО_ЗАПРОСА`: новый POST при этом не отправляется.
Для повторного POST с тем же телом используйте прежний `--idempotency-key`.

В стандартном Compose без профиля `worker` задачи остаются в очереди.
Для выполнения поиска нужен работающий worker с каталогом и провайдером билетов;
клиентский скрипт эти зависимости не запускает.

## Подключение фронтенда

По умолчанию API разрешает CORS для `http://localhost:5173` и
`http://127.0.0.1:5173`. Фронтенд обращается к
`http://localhost:8000/api/v1/queries`, а не к своему порту 5173.
Предварительный браузерный `OPTIONS` обрабатывается автоматически;
разрешены `GET`, `POST` и заголовки `Content-Type`, `Idempotency-Key`.
JavaScript может читать ответные заголовки `Location` и `Retry-After`.
Отправка cookies через CORS не включена; для текущего API она не требуется.

Для других адресов задайте `UBAS_CORS_ORIGINS` в `.env`: список полных origin
через запятую, без пути. Пустое значение отключает доступ с других origin.
Compose передаёт настройку API. После изменения конфигурации или кода
пересоберите и пересоздайте контейнер API; при обновлении образа остановите
старые API и worker перед применением миграций, как описано выше.

## Стек

- Python 3.14.
- SQLAlchemy ORM/Core для PostgreSQL и SQLite, Alembic для миграций.
- [uv](https://docs.astral.sh/uv/) — зависимости, виртуальное окружение и сборка.
- [Ruff](https://docs.astral.sh/ruff/) — линтинг, сортировка импортов и форматирование.
- [mypy](https://mypy.readthedocs.io/) — строгая статическая проверка типов.

## Быстрый старт

Установите uv по [официальной инструкции](https://docs.astral.sh/uv/getting-started/installation/).
Затем выполните:

```shell
git clone https://github.com/UBAS-KurganDev/backend.git
cd backend
uv python install
uv sync --locked
```

`uv sync --locked` создаёт `.venv` и устанавливает проект вместе с зависимостями
разработки из `uv.lock`. Команды через `uv run` не требуют ручной активации окружения.

## Проверки

```shell
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
```

Автоматическое исправление поддерживаемых ошибок и форматирование:

```shell
uv run --locked ruff check --fix .
uv run --locked ruff format .
```

Настройки Ruff и mypy находятся в `pyproject.toml`.

Регрессионные проверки API, планировщика и worker:

```shell
uv run --locked python -m unittest discover -s tests -v
```

При заданном `UBAS_TEST_DATABASE_URL` также выполняются конкурентные проверки
на настоящем PostgreSQL. Имя тестовой БД должно начинаться с `ubas_test_`:
проверки очищают её очередь. Без этой переменной PostgreSQL-проверки пропускаются.
CI по-прежнему запускает только Ruff и mypy.

Для настройки эвристик задайте `UBAS_PLANNER_CONFIG_PATH` — путь к JSON
`PlannerConfig`, одинаковому для API и worker. По умолчанию поддерживается RUB;
другие валюты требуют `price_references` и соответствующих данных провайдера/виз.
Подробности — в [routing.md](docs/routing.md).

## Зависимости

```shell
uv add <package>
uv add --dev <package>
uv remove <package>
```

Команды обновляют `pyproject.toml` и `uv.lock`; оба файла нужно коммитить.
Для целевого обновления зависимости используйте `uv lock --upgrade-package <package>`,
после чего выполните `uv sync --locked` и проверки.

## CI

GitHub Actions при каждом push и pull request устанавливает зависимости по lock-файлу
и запускает Ruff (линтинг и проверку форматирования) и mypy. Тесты и сборка пока
не запускаются.
